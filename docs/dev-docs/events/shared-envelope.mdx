# Shared Event Envelope

These pages define the proposed JSON messages Max patches send to the relay server during a performance. Max sends one event or a list of events in each WebSocket message. The server validates each event and distributes the valid ones to every device in the active session. Clients schedule an event locally, so a timestamped event can begin at the same intended moment on every device.

## Status

The baseline schemas to follow are the initial implementation target. It assumes every connected device receives every event.

:::info[Stretch goals: zones and keyframes]

Zone targeting and keyframed effects are documented as planned extensions, but **are not supported yet**. Max patches must not send `target` or `keyframes` fields until those features are implemented by the server and mobile client.

:::

## Envelope Shape

Every event has the following top-level shape:

```json
{
  "schemaVersion": "1.0",
  "eventId": "00000000-0000-0000-0000-000000000000",
  "type": "type",
  "sequence": 42,
  "sentTimestamp": 1730000000000,
  "epochTimestamp": 1790000000000,
	"relativeTimestamp": 500,
  "payload": {}
}
```

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `schemaVersion` | string | Yes | Schema version. The initial version is `"1.0"`. |
| `eventId` | string | Yes | A unique identifier for this event within the performance session. |
| `sequence` | integer | Yes | A monotonically increasing sequence number assigned by Max. It gives clients a deterministic order when two events affect the same output at the same time. |
| `type` | string | Yes | One of the [supported event types](./event-types). |
| `sentTimestamp` | integer | No | Unix epoch time in milliseconds at which the event was sent by Max. |
| `epochTimestamp` | integer | No | Unix epoch time in milliseconds at which the client should execute the event. |
| `relativeTimestamp` | integer | No | Time in milliseconds after recieving a [Start Event](./start) at which the client should execute the event. |
| `payload` | object | Yes | Properties specific to `type`. |

The event envelope does not include a session ID: the server determines the session from the authenticated Max connection and distributes the event only within that session.

## Frames

A frame is one WebSocket message. Max can send either a single event object or a JSON array of event objects:

```json
[
  { "schemaVersion": "1.0", "eventId": "evt-1", "type": "start", "sequence": 1, "epochTimestamp": 123456789, "payload": {} },
  { "schemaVersion": "1.0", "eventId": "evt-2", "type": "haptic", "sequence": 2, "relativeTimestamp": 500, "payload": {} }
]
```

The array example leaves out timestamps and payload fields to stay short; each event in it has the full envelope.

| Rule | Value |
| --- | --- |
| Events per frame | 1 to 500. An empty list or a list of more than 500 events is rejected. |
| Frame size | No practical limit for a valid frame. The 500-event limit is the one Max will reach. A server safeguard closes the connection for a frame over 8 MiB, far larger than any valid list. See [Acknowledgements](./acknowledgements#oversized-frames). |
| Order | The server processes a list in order and keeps that order when relaying it. |
| Duplicate `eventId` | Within one frame, the first event with an `eventId` is processed and any later event with the same `eventId` is rejected. Duplicates are not yet checked across frames or across a performance. |

The server treats a single event exactly like a list containing one event.

Each event in a list is validated on its own. Valid events are relayed even when others in the same frame are rejected (see [Validation Expectations](./validation)). The server answers every frame with exactly one [acknowledgement](./acknowledgements).

### What audience devices receive

Audience devices always receive a JSON array of events, even when Max sent a single event. A Max frame produces at most one audience frame:

- The array contains only the valid events from the Max frame, in the order Max sent them.
- `ping` events are not relayed.
- If a frame has no events to relay, the server sends nothing to the audience.

Events in an array are not grouped in any other way. Each one is scheduled and executed independently, according to the timing rules below.

## Timing and ordering

- Timestamps can be either relative or epoch. Epoch timestamps are absolute, relative timestamps are based on a [Start Event](./start). If both are `null` or `0` the event takes place immediately. An epoch timestamp takes precedence over a relative timestamp if both are present and in the future.
- Timestamped events should be sent sufficiently before their `epochTimestamp` for the server to relay and clients to queue them. A `null` or `0` timestamp is appropriate for an immediate effect, but is not synchronized across devices.
- Clients execute each event independently. Multiple events with the same timestamp may therefore begin together (ex: a `haptic`, `screen`, and `caption` event).
- When two events control the same output at the same timestamp, the higher `sequence` value takes precedence. A newer haptic replaces a haptic already playing; a newer screen event replaces the current screen effect.
- Durations (included in the payload) are expressed in milliseconds. A duration ends the event and restores the output to its state immediately before that event, unless a later event has already replaced it.

## Common payload value rules

| Value | Rule |
| --- | --- |
| `durationMs` | Non-negative integer milliseconds. `0` indicates until replaced or the asset is complete |
| `intensity` and `brightness` | Number from `0` through `1`, inclusive. These are normalized intent values; the mobile app maps them to device capabilities. |
| `color` | Six-digit sRGB hexadecimal string in the form `"#RRGGBB"`. |
| `assetAlias` | A unique non-empty string of the name of the file registered for the session and downloaded by the device during session join. |
| `transitionMs` | Non-negative integer milliseconds to fade between the current state and the new event state. `null` or `0` indicates immediate change.  |
